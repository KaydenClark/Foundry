# Recovery design record

Terminology is preserved for design work; descriptions of runtime behavior are
historical design claims, not acceptance or deployment evidence.

# Historical Foundry design lexicon

These terms are the shared language for WORKSPACE. Project-local domain language
may add detail, but it does not silently redefine these workspace contracts.

Onward: [AGENTS.md](AGENTS.md) owns the rules these terms describe,
[BLUEPRINT.md](BLUEPRINT.md) owns the architecture they name, and
the shared role-skill catalog holds delivered stances such as `role-engineer`,
while [Foundry/Roles/](Foundry/Roles/) holds the six contracts still awaiting
S-016 migration.

| Term | Meaning |
|---|---|
| **Agent** | One running model process or delegated task. An agent performs work under one loaded role and the nearest project controls. An Agent *deliberates* — it reasons within a role and a Job Order — as opposed to a **Pawn**, which automates. Neither holds ambient authority over Actuality. |
| **Pawn** | A deterministic, non-model actor that executes bounded triggers or Job Orders. Pawns automate; Agents deliberate. Neither has ambient authority over Actuality. Generated **Projection** captures are written by Pawns through deterministic render, project, and mirror operations; this is a convention for those artifacts. (Foundry rework, item 27.) |
| **Run** | One attempt by one Agent at one Job. Durable continuity belongs to the Factory's durable records and stores — Canon, the Grounding Journal, and Wiki documents — never to an Agent's chat or session context. (Foundry rework, item 3.) |
| **Role** | A Foundry-owned authority and responsibility contract loaded for one task. Loading a role means the current agent adopts that stance in its own context — instructions for how to be X — and never by itself spawns a sub-agent; separate agents exist only when Captain explicitly dispatches separate tasks. Roles are not copied into projects. Engineer is delivered as the shared `role-engineer` skill; six legacy `Foundry/Roles/*.md` contracts remain during S-016 migration. |
| **Stance** | A contract an agent adopts for one task — Inputs, **Authority**, Operating Loop, Hard Stops, Handoff. A skill says *what to do*; a stance says *what you may decide and who you are while deciding it*. It is loaded alongside a skill of any tier, composes nothing, and carries no **composition tier**. Delivery uses one flat shared-home path named `role-<name>` (S-016/S-026), never a nested discovery folder. Supersedes filing stances as a Complex tier. |
| **Composition tier** | Where a skill sits on the composition ladder, measured by **depth**: the longest chain of skill *calls* beneath it, counted from 0. **Primitive** (0), **Compound** (1), **Assembly** (2–3), **Complex** (>= 4). Only "runs it as a step" builds depth — routing to a skill, exiting to one, and citing one do not. Depth measures what a skill is *made of*, never how many options it lists: a skill that names alternatives without running them (`ask-workbench`) is a primitive. Read the ladder industrially — parts, materials, assembled machines, the whole facility — matching Foundry / Forge / Hall / Gatehouse. **Its purpose is to tell you how heavy a skill is before you run it.** A **stance** is not on the ladder at all. **The tier follows the code:** a skill that *should* compose something is rewritten first and reclassified after; nothing is ever filed at an aspirational tier, so a Primitive listing is a work queue rather than a verdict. |
| **Primitive** | A skill at **depth 0**: it makes no skill calls, does one thing with its own instructions, and bottoms out every chain that reaches it. `grilling` is the prime example. Distinct from **model-invocable**, which says who may *call* a skill rather than what it is made of; the two are independent facts about the same skill. |
| **Compound** | A skill at **depth 1**: it calls primitives and nothing deeper. `grill-me` calling `/grilling` is the minimal form. Adding a primitive to a skill is what promotes it — `lexicon` is the reference case: *"the primitive we add to a bunch of skills to make them compound."* |
| **Assembly** | A skill at **depth 2–3**: it calls compounds, running an ordered line of skills toward one outcome. `make-it-so` is the anchor — `/to-docs`, `/to-spec`, `/to-tickets`, `/save` in sequence. Retires the placeholder name "stacked". |
| **Complex** | A skill at **depth 4 or beyond**. Read industrially — a site of many assemblies, as in an apartment or refinery complex — never chemically; the chemical reading ("made of many parts") collided with **Compound**. Reaching it is a graduation *and* a watchlist entry, never an order to flatten: a conformance check **reports** Complex members and never fails on them. Born empty 2026-07-27; the deepest live chain is 2. |
| **Model-invocable** | A skill the agent, or another skill, may call on its own — the frontmatter state where `disable-model-invocation` is absent. Its counterpart is an **entry point**: owner-fired only. A thin owner-gated entry point wrapping a model-invocable skill is the standard pairing, as `grill-me` wraps `grilling`. **Invocation invariant:** a skill that is *called* must be model-invocable, and an entry point must never be called — only routed to or exited to. It constrains **in-edges, not out-edges**, so an entry point calls freely; the corollary is that an entry point is always the top of its own chain. Renames the 2026-07-25 use of "primitive" for this property, which now belongs to composition depth. |
| **Team** | The collective agents currently working under WORKSPACE roles. Captain coordinates the Team. |
| **WORKSPACE operating team** | the owner plus one persistent **Servitor per host** — the Mac Mini (`1`) and the Windows PC (`2`), with a spun-up cloud host adding another — each currently powered by a replaceable **Engine** (Codex or Claude). Supersedes the earlier "four fixed seats" reading: there are durable host Servitors, not four fused host+model beings (governance grilling, 2026-07-24; items 32–33). |
| **Servitor** | The emergent whole of a Foundry running as one: the persistent context and continuity that makes each activation the same being — not the Engine, not any single Workbench/Agent/plane, but all of them animated together. **One Servitor per host** (Mac Mini, Windows PC, or a spun-up cloud instance). It is asleep-but-continuous — continuity lives in the durable stores (Canon, the Grounding Journal, the Wiki), not in any running process — so swapping the Engine or restarting a process does not create a new Servitor. (Governance grilling, 2026-07-24; item 32.) |
| **Engine** | The model currently powering a Servitor (Codex, Claude): a replaceable power source, not part of identity. "Claude on the Mac Mini" means "the Mac-Mini Servitor, currently on the Claude Engine." The old fused seat splits into two orthogonal axes — **which host** (the Servitor, durable) × **which Engine** (the model, floating). (Governance grilling, 2026-07-24; item 33.) |
| **Servitor seat** | The composite label `Servitor-<host><engine>` for one *running* host×engine pair — e.g. `Servitor-1B` = the Mac-Mini Servitor currently on the Claude Engine. The **host digit is the durable Servitor** (`1` Mac Mini, `2` Windows PC) and the **letter is the replaceable Engine** (`A` Codex, `B` Claude); the two are orthogonal axes composed only when naming one specific running pair, **not** a fused fixed identity (`Serv` as in server, not servant). the owner remains the owner and is not numbered. A running pair may drive many **Agents** at once, including sub-agents in one chat; those are Agents under the Servitor, not additional Servitors. The label identifies a participant; it grants no authority and makes no private model memory canonical. Supersedes the prior host-and-model *pairing-as-identity* reading (governance grilling, 2026-07-24; items 32–33). |
| **Factory** | A host-scoped deployment of the Foundry. A Factory has exactly one Facility Steward/Servitor, may contain many Workshops, and connects outward through sockets and modules. The hierarchy is Foundry (portable product) → Factory (host deployment) → Workshop (one project) → Workbench (that project's harness). (Foundry rework, items 1, 1B, 4.) |
| **Workshop** | One project inside a Factory. Its operating surface is that project's **Workbench**. Called a *room* or *project room* in older notes; Workshop is the formal term. (Items 1B, 4.) |
| **Facility Steward** | The Servitor's persistent, model-neutral, human-facing identity, continuous across activations. One per Factory. Captain, Engineer, Auditor, and Planner are **temporary role skills the Steward or an Agent adopts for one task** — they are stances, not persistent beings. (Items 1A, 17.) |
| **Entrance** | The human-facing, channel-neutral surface through which the owner communicates Intent into a Factory and requests a bounded wake. Formally replaces the earlier term *Door*. A provider desktop app is a direct engine Entrance; CIC is the preferred typed or voiced Entrance. An Entrance offers only pre-determined Intent options: it cannot turn a Factory on or off, authorize work, write Canon, or execute Actuality. A microphone is a voice control *inside* an Entrance, not the concept itself. (Items 2, 29; S-035.) |
| **Captain** | The user-facing Sol coordinator: conversational with the owner, reads the generated portfolio view, assigns workers, protects writer lanes, and reviews verified handoffs. A **temporary role skill**, not a persistent identity — the persistent one is the Facility Steward (item 17). Whether Captain retires into machinery entirely is an open grilling question, not settled Canon. |
| **Chain Engineer** | The sole durable writer for one validated, finite direct project assignment. It advances only the manifest's lifecycle-eligible ordered specs, while Scout and Auditor lanes remain read-only. A **temporary role skill** under the Facility Steward (item 17). Whether it retires into a chained-Job-Order dispatch pattern is an open grilling question, not settled Canon. |
| **Scout** | A bounded Luna reconnaissance role that verifies one assigned project and must update its canonical Taskboard Scout Status before reporting back. Scouts do not alter code, specs, tickets, or runtime state. |
| **Designer** | The role that tests whether proposed work provides real project value and sharpens the product decision. |
| **Planner** | The role that turns settled direction into canonical specs, tickets, priorities, dependencies, and owner gates. |
| **Engineer** | The shared `role-engineer` stance that the current agent adopts to implement one claimed vertical slice and leave verified, documented, remotely recoverable work. Invoking it does not spawn a sub-agent. |
| **Tracer bullet (vertical slice)** | A lean but complete unit of work that pierces every horizontal layer of a project's stack — schema, service, interface, and test — for one narrow behavior, so it is demoable on its own and returns end-to-end feedback. Captain and Planner cut work into tracer bullets; a slice that touches only one layer is a horizontal shard, not a tracer bullet. The `/tracer-bullet` skill is the discipline for cutting, ordering, and assigning them. |
| **Auditor** | An independent read-only role that tests correctness, safety, value density, and acceptance evidence. |
| **Sitrep** | A conversational, read-only situation report using the smallest sufficient live scope. It is a **read of Projection** spoken into the conversation, not an authored artifact by default. It answers what matters now and delegates Scout only when deeper evidence is needed. In flight mode it routes one named Canon-backed Job Order and writes the first ordered handoff; it never grants scope or opens a work lane. |
| **Preflight** | The deterministic, read-only launch gate (S-023, extended by S-037): it verifies the Canon-backed Job Order against live Actuality, every repository and target, active-lane collisions, Next gate and blockers, protected pins, proof, recovery, and an attainable landing/closure path. A pass is a freshness-bound fingerprint and its outgoing handoff to Launch-flight; the current Canon and owner scope supply authorization, and a Steward-accepted Launch-flight opens the flight lane. It fails closed and mutates nothing. **Two bands:** blocking failures exit 1 for an owner or named external gate; reconcilable record/source drift exits 3 so an agent verifies and corrects bookkeeping before rerunning. `--audit` diagnoses all tickets but never launches one. The current S-023 script remains authoritative scaffolding until the Sandcastle retirement trigger lands. |
| **Launch-flight** | The Steward-accepted transition from a passed Preflight handoff into one claimed isolated writer lane for one Canon-backed Job Order. It binds actor, role, run, worktree/branch, exact source and target state, scope, proof, recovery, and landing contract; it is not a synonym for implementation. |
| **In-flight** | The bounded implementation stage inside an accepted Launch-flight lane. It may implement, test, document, checkpoint, and prepare a remotely recoverable candidate only inside the Job Order; it cannot self-claim, self-accept, widen scope, or merge. |
| **Landing-check** | The independent, read-only acceptance stage immediately before Land. It is bound to the exact remotely recoverable candidate SHA and checked target state, reports findings first, and is invalidated by every candidate change. |
| **Land** | The delivery stage that consumes an accepted Landing-check handoff, fetches and revalidates the target, tests the exact integration candidate, and advances only the Job Order's authorized remote `integration` with an explicit non-force mechanism. Delivery is not closure and never implies `integration` to `main`. |
| **PostFlight-check** | Preflight's outward counterpart and the terminal integrity stage after every Land outcome. It starts from verified post-Land Actuality and proves that Canon, Grounding, Enduring Context, Intent, Projection, recovery, claims, activation, and ordered handoffs represent that exact state. A missing Integration PR or merge routes one bounded repair handoff to a fresh chat; the verifier waits and rechecks fresh evidence. It reports a flight as landed or closed only when the required state agrees, otherwise preserving `delivered-unclosed` or `recovery-required` with the exact repair. |
| **Steward-serialized** | Lifecycle schema v1 and the honest current fallback until v2 exists: the Facility Steward reads the current Job Order, claim, receipts, lanes, and live state and records the only safe successor. If one safe answer cannot be established, nothing advances and the owner receives one bounded question. It is procedural serialization, not machine atomicity. After successful v2 initialization it is read-only historical Grounding, never an alternate live writer. |
| **Cooperative Git CAS** | S-037 lifecycle schema v2's conforming-writer serialization boundary: one legal direct descendant of an exact private lifecycle-ref tip, pushed and read back with lifecycle state plus one Journal event in the same commit. Exact-tip comparison detects stale cooperative writers; deletion, force-update, unauthorized-writer, and validator-bypass prevention require separately verified remote policy. |
| **Lifecycle receipt** | A single-use, fact-bound Preflight record whose canonical JSON digest binds authority, actor/Run, scope, policy, repositories, refs/SHAs, lane state, exact lifecycle tip, dependencies, proof, gates, and closure path. Launch-flight rereads every bound fact before CAS. Successful CAS consumes it; conflict invalidates it; ambiguous push is fetched; pre-CAS failure may retry only after complete reread and unchanged-tip proof. UTC time is diagnostic, not validity authority. |
| **Sandcastle** | The provider-agnostic TypeScript framework (`github.com/mattpocock/sandcastle`) for isolated agent execution — sandboxes, worktrees, branch strategy, merge-back, and lifecycle hooks — adopted as **the framework the Foundry's guards get rebuilt inside**. **"Absorb" does not mean Sandcastle already ships our guards:** it ships hooks and custom sandbox providers precisely so a consumer supplies its own rules, so its not having them pre-built is expected, not a gap. What dies in the absorbed pile is the **bespoke standalone WORKSPACE guard tooling**; the **rules** those tools enforce (no push to a protected branch, no switching a protected checkout, verify before launch) **survive as Sandcastle hook config**. Bespoke guard *tooling* is scaffolding — *"we just needed the guards to stand there while we stood up the castle"* — and because that tooling is tracked in the root repo, deleting it *is* retiring it: git history is the void, so no "retired but preserved" state is kept and no dead code is kept alive. The reach-around guard (`SC-4`) is the exception that proves the frame: it is **real architecture, not scaffolding** — build it, shaped as an importable function plus a thin CLI so its later move into a hook is a relocation, not a rewrite. (`SC-13`/`SC-13A`, locked 2026-07-25.) The **retirement trigger is still open** (`SC-13B`), so every S-023 guard stays live and authoritative until Sandcastle actually lands. |
| **Protected checkout** | A shared checkout that live tooling reads from, enrolled with an owner-edited branch pin in `tools/protected-checkouts.json` (today: the canonical Forge). Agent flows never switch, reset, stash, or check out one — agents get registered worktrees. Preflight fails every launch while a protected checkout is off its pin, and a post-checkout tripwire flags the switch for First Responder the moment it happens; a deliberate owner switch is recorded by updating the pin. |
| **`make it so`** | the owner's exact authorization passphrase, usable with or without a grilling. It confirms pending approvals, locks the settled design and implementation scope (the matching grilling notepad when one exists, otherwise the current conversation's settled decisions), and authorizes the full pipeline — to-docs, to-spec, to-tickets, save-plan, implement — within standing workspace boundaries, with every checkpoint committed and pushed to the remote canon. Pushed tickets are scheduled by Captain discovery. It ends an active grilling; a missing notepad is never an error. Similar phrases do not carry this meaning. |
| **Servitor Foundry** | The reusable, vendor-neutral assistant OS. Its **core is the composed whole: the Canon-declared Halls + Foundry Modules**. The current Canon roster has thirteen Halls; that count is amendable, not a product invariant. "The Foundry" alone carries this meaning. It is a **governance system** — it takes a plain Workbench (one room's rules, memory, and tools) and makes it able to run a whole *set* of rooms by adding sockets, modules, and the machinery to connect, monitor, and maintain every room. It is the **product**; **WORKSPACE** is the owner's **deployment** of it onto each host (Mac Mini, PC). It must be packageable and deployable; a *public-facing* distribution is a separate axis, not needed yet. |
| **WORKSPACE (instance)** | the owner's instance of the Servitor Foundry: the folder the Foundry is installed into and manages — projects, Wiki memory, runtime, and secrets. Product : deployment; the workspace name stays WORKSPACE. |
| **Foundry core** | The complete reusable product that travels to a fresh deployment: **the Canon-declared Halls + Foundry Modules, composed**. The current declaration happens to contain thirteen Halls; an explicit Canon amendment may change that roster. Core is the ownership boundary around both families, not a third peer beside Modules and not a synonym for the Halls alone. A component may be `core, not-yet-extracted` when it belongs to either family but still lives in the instance tree pending extraction (tracked as a backlog, never a permanent parking lot). |
| **Hall** | The Foundry's organizational tier: the rooms of the factory floor, and the tier an agent enters to get its work, its skills, and its stance. The currently declared roster has **thirteen Halls** — Intake, Validation, Gatehouse, Orchestration, Design, Knowledge, Scheduling, Forge, Production, Assay, Ward, Gauge, and provisional Shipping. That count is current Canon, not a permanent product invariant: an explicit Canon amendment may add, retire, merge, or split Halls while preserving identities and migration evidence. A Hall is a **complete vertical boundary**: its own Pawns, its own skills, its own lifecycle. Tickets are the explicit interface between Halls. A Hall is not a socket: sockets are *housed inside* Halls. Halls are the tier the retired capitalized **Foundry Sockets** was reaching for and named after its contents. |
| **the Assay** | The Hall that judges quality: read-only evaluation, normalized evidence, and archive-readiness verdicts. To *assay* is to test metal for purity and issue a hallmark — it reports and changes nothing about the metal, so the name carries the read-only contract. Renames the earlier **Audit Engine**. Frees the word *audit* for the Gatehouse's badge-scan trail. The **Auditor** role name is open (candidate **Assayer**, not decided). |
| **the Ward** | The Hall that checks fit: room health, integration, and conformance across the deployment — the Assay judges *quality*, the Ward measures *fit*. Renames the earlier **PIP** / **Personal Intelligence Platform**. |
| **the Gatehouse** | The Hall that supplies mandatory structural passage, scan, containment, clearance, and receipt infrastructure. Gatehouse authorizes nothing: it records and reports protected passages, and does not route, validate, decide policy or scope, assign work, or supply authorization, which comes from Canon, Clearance, and owner scope. |
| **Foundry Sockets** | **Superseded by Hall.** The retired capitalized-plural family term for the Foundry's reusable system-and-contract layer — the Forge, Audit Engine, PIP, roles, scheduler, automation review, and the socket registry. It named the tier after its contents and left one word carrying two meanings; the tier is now a **Hall** and lowercase singular **socket** keeps only the capability-contract sense. Retained here so the old name resolves; do not use it for new writing. S-027/TK-003 completed the physical cutover to `Foundry/Halls/`; no compatibility alias remains. |
| **Foundry Module** | A standalone-usable component that implements **one or more** Foundry sockets while remaining replaceable behind those stable contracts. **Cardinality is asymmetric many-to-many, not 1:1** — the earlier singular "implements *a* Foundry socket" was stale phrasing, never a rule. One module commonly fills *many* sockets, and that is the dominant shape: *"more often than not it will be 1 module : many sockets."* One socket may have many *candidate* modules but exactly one **active** binding at a time (messaging must support swapping Slack for Discord). CIC is the worked case — it needs recall **and** messaging **and** interface simultaneously; recall ↔ OpenBrain is closest to 1:1. Most modules need only messaging and/or recall beyond their own primary socket; broad access is the exception. (`SC-8`, locked 2026-07-25.) A Module producer belongs under `Projects/` when enrolled; its installed product belongs under `Foundry/Modules/`. CIC produces the Dashboard product and OpenBrain produces the Brain product. Modules are part of the Foundry core, not external additions to it. |
| **Blessed module** | A **fit** predicate, not an authorship one: a Module that **plugs into its socket cleanly**, with no forcing. Whoever built it — *"if somebody else builds a module that works with the Foundry, it will also be a blessed module."* the owner built today's blessed modules only because he built the Foundry. The inverse is the sharp edge: *"a Module that doesn't really connect into any of our sockets and we have to force it — that's not a blessed module."* **Blessing is revocable and condition-based, not a permanent title** — the Spotify Atlas is the worked negative example: not blessed today, because it is not working right. Any roster is therefore a **current status to be re-derived from fit**, never a membership list: OpenBrain, CIC, and Slack fit today; Discord is paused, superseded by Slack for messaging delivery. |
| **Socket** | A **capability connection contract, and only that** — stable, capability-named, exposed through an open registry. A socket is **housed inside a Hall**; it is never itself a Hall, a component, or an engine. (The earlier "fundamental native component" sense is retired: a contract is not an executable thing, and the Halls are *"the places the sockets are created and housed."*) The contract and registry travel with the Forge; the *binding* (which Module is plugged in, its credentials/config) is instance data; the *implementation* belongs to the Module. The Module filling a socket can change without renaming the socket. **No reach-arounds:** an agent or room reaches a Module *only* through its socket, never by direct filesystem reach-around — a rule that is **stated but not yet enforced** (see **Socket contract registry**). Today's *active bindings*: recall (OpenBrain), messaging (Slack, with Discord the paused swap candidate), and interface (CIC). Read that as one active binding per socket, **not** as 1:1 pairs — CIC is designed to need recall and messaging too (`SC-8`). The live binding table (`workbench/wiki/Machine/Project Source Registry.md`) is still socket-indexed with a single bound-entity column and cannot yet express one module's several simultaneous bindings as a queryable relationship; that reshape is recorded follow-on work, not done. |
| **Foundry area** | The root `Foundry/` folder: a local, daily-cadence aggregation of the Foundry components across their separate remotes. Deliberately not one vendored repository; user project rooms stay under `Projects/` on the slower cadence. **Correction (2026-08-02):** "across their separate remotes" holds only for **Foundry Modules**; **Halls have no separate remotes** and travel only as contents of the **Foundry product** (see **Three-tier ownership model** and the **Hall-vs-Module return leg**). |
| **Three-tier ownership model** | The Foundry ownership boundary: the Halls, the Foundry Modules with their separate remotes, and the WORKSPACE instance with its thin `example/workspace` mirror. The first two tiers together are the Foundry core. Every piece remains standalone-usable and vendor-neutral; the Foundry is where they compose. This supersedes the narrower term **three-repo model**, because Halls and Modules each span multiple repositories. **In motion (S-024):** the Halls are folding into `example/Foundry` as tracked source rather than separate remotes — the Forge already has, and the Assay and the Ward are following, at which point their standalone remotes are retired. Only Modules stay remotely installed. |
| **OpenBrain** | The blessed Foundry Module filling the recall socket: the owner's derived, private memory/context API. **The Wiki is the documentary store; recall is how you ask it.** The Wiki stores durable documents in the Workbench; OpenBrain recalls them through derived retrieval. It is never canonical for anything with a Git/Markdown home, and is the home for capture-class DB-native data Git was never good at. |
| **Surface** | A human-facing point where the Foundry meets the owner; CIC, Slack, and Obsidian are surfaces. A surface renders or notifies; it never becomes a second store of truth. |
| **`recall`** | The read verb for OpenBrain: derived, provenance-bearing retrieval. What an agent recalls never outranks a newer verified live file. |
| **`mirror`** | The standing property of being a faithful, fail-closed derived copy of canonical state. A stale mirror reports staleness rather than pretending freshness. |
| **`project` (verb)** | The act of writing canonical state into a derived read model, as sync-and-verify projects task state into OpenBrain. Projection is one-way; nothing projected becomes the authority. |
| **`capture`** | Writing capture-class, DB-native data — thoughts, creative work, personal corpus — into OpenBrain: data born in the database with no Git/Markdown home. |
| **`render`** | Making a derived view visible: a read model drawn for a human or written to a generated projection file. |
| **`notify`** | An outbound Foundry-to-the owner push through the messaging socket, always carrying its originating Servitor's authorship (its host plus current Engine). |
| **`dispatch`** | Captain sending work to a seat or agent. |
| **`route`** | Directing a question or reference to its owning canonical source. |
| **Activation levels** | The scheduler's named cost/capability hierarchy (S-015). **L0 Sleeping** runs deterministic, no-model checks and exits when nothing changed; **L1 Dispatcher** (Captain, Luna) decides whether AI work is warranted and coordinates; **L2 Worker** executes one slice and audits it; **L3 Executive** (Sol) resolves ambiguity, novel architecture, or conflicts as an escalation path only. Most scheduled passes must live in L0/L1; L2/L3 are entered only for real work. **L0.5 Sweep** sits between L0 and L1: a transient, self-extinguishing, deterministic micro-wake where a Pawn wakes just enough to check and report, with no model reasoning. It is the only self-extinguishing level and always announces one of two exits — back down to L0, or up to L1 by waking the Steward. (Item 36 — approved Canon; the shipped S-015 registry still enumerates L0–L3 only, so this is Canon ahead of code and the implementation gap is unclosed.) |
| **Model roster** | Our canonical cross-provider mapping from activation tier to one model per provider (S-015): L3 Sol `gpt-5.6-sol` / Fable 5 `claude-fable-5`; L2-complex Terra `gpt-5.6-terra` / Opus 4.8 `claude-opus-4-8`; L2-default Codex-Spark `gpt-5.3-codex-spark` / Sonnet 5 `claude-sonnet-5`; L1 dispatcher Luna `gpt-5.6-luna` / Sonnet 5 `claude-sonnet-5`. Codex-Spark is the kept default worker; Sol/Fable is never a managed default. Haiku 4.5 was dropped from the roster (2026-07-20). |
| **the Forge** | The Hall that develops, tests, releases, and distributes the reusable Workbench — *"the Forge builds the Workbench."* Renames the earlier **Workbench Factory** (off-metaphor: a foundry *contains* forges, and "Workbench Foundry" would collide with Servitor Foundry). The mechanical rename of the `Workbench Factory/` folder, its remote, and its references is tracked in S-008; the name is decided now. **Clarification (2026-08-02):** WORKSPACE holds the Forge's live producer source at `Foundry/Halls/Forge`; `example/LLM_Workbench` is a published **product** remote, never the Forge's authoring source. The Forge is also the performer of the mechanical **publish** (see **Publish pipeline**). |
| **Workbench** | The operating surface of one project or room: the seven-file Workbench Contract, the six-lane `workbench/` support directory, and shared skills dependency. It supplies generic structure, vocabulary, procedures, projection, specs, Wiki routing, provisional decisions, handoffs, feedback, and conformance; Foundry adds the cross-room and runtime capabilities ([ADR-0013](workbench/docs/adr/0013-seven-file-workbench-contract.md), [ADR-0017](workbench/docs/adr/0017-workbench-support-directory-has-six-lanes.md), [ADR-0015](workbench/docs/adr/0015-workbench-base-and-foundry-capabilities.md)). |
| **LLM Workbench** | The **published, cleaned copy** of WORKSPACE's own live root-room Workbench: the same design with instance data (Wiki, secrets, runtime) stripped, continuously (re-)authored *from* the live instance rather than built separately. **Retires the earlier reading — "the same thing as the Workbench, one concept, not a package-vs-product pair."** That line taught agents the live instance and the published product were one artifact, and it is why more than one audit built the wrong model of the Forge. There is a live-vs-published distinction; there is still no *second design*. Change flows outward only: edits are made live in WORKSPACE and reach the published copy through the **publish pipeline**, never the reverse. ("Foundry Workbench" stays retired as a generic term because the Foundry is the composed Halls-and-Modules product, not one special Workbench.) (`SC-9`, locked 2026-07-25.) |
| **Published copy** | WORKSPACE runs simultaneously as a live **Foundry** (the whole — a connected system of rooms) and, at its root, a live **Workbench** (one room). ## Governance

| Term | Meaning |
|---|---|
| **Foundry Contract** | The imperative, behavioral half of a Workbench — how an agent must act: `AGENTS.md` and its thin `CLAUDE.md` bridge. |
| **Foundry Canon** | The binding current-state rules used to authorize, constrain, and verify work, with definitions in the Lexicon and architecture summarized in the Blueprint. It describes the role of those rules in an operation, while ADRs and SPECs serve as Grounding and the generated Taskboard reports as Projection ([ADR-0001](workbench/docs/adr/0001-planes-classify-operations-not-artifacts.md), [ADR-0002](workbench/docs/adr/0002-binding-rules-stay-in-current-controls.md), [ADR-0008](workbench/docs/adr/0008-adrs-and-specs-record-grounding.md)). |
| **Wiki** | The Workbench's durable, navlinked document store and knowledge base. Storage location assigns no Governance Plane: a note's role in the operation determines whether it is a consulted reference, evidence, or the target of a change, and Wiki content supplies no independent authorization ([ADR-0001](workbench/docs/adr/0001-planes-classify-operations-not-artifacts.md)). |
| **Taskboard** | The canonical, generated active-work report of eligible work, claims, blockers, owner decisions, and next gates, serving as **Projection**. Its report does not create blockers, authorize work, or override its sources (items 18/34; [ADR-0001](workbench/docs/adr/0001-planes-classify-operations-not-artifacts.md)). |
| **Governance Planes** | The six roles artifacts play in one operation: **Actuality**, **Canon**, **Grounding**, **Enduring Context**, **Intent**, and **Projection**. No file has a permanent plane; a rule file is Canon when used to authorize a change and Actuality when it is the target of one ([ADR-0001](workbench/docs/adr/0001-planes-classify-operations-not-artifacts.md)). |
| **Authority Order** | The protection and earned-access order for the six Governance Planes, from Actuality as most protected through Canon, Grounding, Enduring Context, Intent, and Projection as least protected. It does not determine truth precedence, resolve disagreements automatically, or require visiting every plane (notepad item 15A). |
| **Actuality** | The target being changed in an operation, including files, source, runtime, and verified state. Change requires current Canon, Clearance, and explicit owner scope; direct owner instruction assigns roles, and a Job Order carries them across chats when one is in force rather than as a precondition for the work ([ADR-0001](workbench/docs/adr/0001-planes-classify-operations-not-artifacts.md), [ADR-0010](workbench/docs/adr/0010-job-orders-coordinate-work-across-chats.md), [ADR-0021](workbench/docs/adr/0021-job-orders-are-a-form-not-a-precondition.md)). |
| **Canon** (plane) | The binding current-state rule authorizing and constraining an operation. Owning controls carry the complete requirement; links to ADR rationale or SPEC evidence do not supply independent authority ([ADR-0002](workbench/docs/adr/0002-binding-rules-stay-in-current-controls.md), [ADR-0008](workbench/docs/adr/0008-adrs-and-specs-record-grounding.md)). |
| **Grounding** | The evidence about the intended truth or whether work was done correctly, including accepted ADRs, SPECs, verification, and audit findings. It supports, tests, informs, or justifies Canon and may satisfy or fail an existing gate, but does not independently authorize work or invent a gate ([ADR-0008](workbench/docs/adr/0008-adrs-and-specs-record-grounding.md); item 14 amendment). |
| **Enduring Context** | The durable reference consulted in an operation, including the promoted grilling notepad that retains the debate and corrections. It informs work without independently authorizing changes or creating mandatory requirements ([ADR-0001](workbench/docs/adr/0001-planes-classify-operations-not-artifacts.md), [ADR-0008](workbench/docs/adr/0008-adrs-and-specs-record-grounding.md)). |
| **Intent** (plane) | The request or proposed work in an operation. Direct owner instruction can supply explicit owner scope and role assignment; an Agent or Pawn cannot manufacture that authority, and unsettled notepad items remain unpromoted ([ADR-0001](workbench/docs/adr/0001-planes-classify-operations-not-artifacts.md), [ADR-0010](workbench/docs/adr/0010-job-orders-coordinate-work-across-chats.md); item 22). |
| **Projection** | The reporting role that describes Actuality through source-derived views, including the generated Taskboard, without authorizing changes to its inputs. Generated captures are Pawn-written, source- and freshness-visible artifact conventions; a report cannot grant scope, satisfy Preflight, or accept Launch-flight ([ADR-0001](workbench/docs/adr/0001-planes-classify-operations-not-artifacts.md), [ADR-0003](workbench/docs/adr/0003-full-crud-with-artifact-conditions.md)). |
| **Grounding receipt** | The truthful record every workspace conversation that investigates or advances a workstream appends before yielding, at the conversation boundary — even when the work is blocked, incomplete, or changed no Actuality. It names the Plane worked, any Job Order and ticket, observations or decisions, actions, verification and unknowns, and the exact next gate. It goes to the owning stable spec, or to the session notepad and commit message when the work has no owning spec; creating a spec is never a precondition for it. A receipt preserves evidence and does not authorize work or promote evidence into Canon ([ADR-0021](workbench/docs/adr/0021-job-orders-are-a-form-not-a-precondition.md)). |
| **Grounding Journal** | The accepted minimum operational ledger: append-only Intent disposition; Job Order claim/handoff/block/completion; run activation/outcome; Grounding receipts/verdicts; and Mirror freshness metadata without duplicated Canon or Intent content. Knowledge owns its schema, append validation, digest chain, retention, replay, and recovery verification through the `grounding-journal` socket. In lifecycle schema v2 its event shares the authoritative private commit/tree with lifecycle state. TK-012 must implement it before Canon claims a live Journal exists. |
| **Shipping gate** | One of three named gate types that verify a protected transition: **Proof** (repeatable mechanical evidence — tests, validation, scope, save/push, required references), **Audit** (an independent Auditor verdict on Grounding), and **Owner Command** (the owner's explicit Intent-plane authorization). Owner Commands cannot be created by an Agent or Pawn; Proof and Audit outcomes live in Grounding. A requirement is not a gate — the gate verifies whether its condition is met. (Item 13.) |
| **Durable packet** | One of the fixed record types through which Agents and Pawns communicate before implementation: **Intent**, **Job Order**, **Claim**, **Handoff / Blocker**, **Grounding Receipt**, and **Audit Verdict**. Mirror derives status from these records rather than being another packet type. The set is intentionally provisional for the first implementation boundary. (Item 14.) |
| **Job** | The durable assigned outcome, scope, and acceptance criteria given to an Agent. A **Job Order** carries the coordination and operation checklist when one is in force; it is never required for the work to proceed, and authority comes from current Canon, Clearance, and explicit owner scope ([ADR-0010](workbench/docs/adr/0010-job-orders-coordinate-work-across-chats.md), [ADR-0021](workbench/docs/adr/0021-job-orders-are-a-form-not-a-precondition.md)). |
| **Job Order** | The durable coordination and tracking form an Intent too large to complete in one chat takes **when one is in force** - never a precondition for that work existing, which the handoff and its session notepad may carry instead ([ADR-0021](workbench/docs/adr/0021-job-orders-are-a-form-not-a-precondition.md)): an operation checklist linking the Workbench Contract, actor's Clearance band, goal, and required evidence. It preserves assigned roles across sessions and agents, with effective authority limited to the intersection of current Canon, issuer Clearance, assignee/tool permissions, and explicit owner scope ([ADR-0009](workbench/docs/adr/0009-job-order-authority-is-an-intersection.md), [ADR-0010](workbench/docs/adr/0010-job-orders-coordinate-work-across-chats.md), [ADR-0011](workbench/docs/adr/0011-job-order-is-an-operation-checklist.md), [ADR-0012](workbench/docs/adr/0012-job-orders-link-to-owning-sources.md)). |
| **Job Order Context** | `CONTEXT.md` inside one active Spec-local Job Order: an append-only bounded message board for important verified facts, questions, decisions, warnings, and coordination notes. It is not authority, a task board, proof archive, transcript, secret store, or substitute for the stage handoff. |
| **Job Order Workflow Runbook** | The binding core procedure in [RUNBOOK.md](RUNBOOK.md#job-order-workflow-runbook) for every Job Order's creation, execution, and completion. The Runbook owns the exact lifecycle and fail-closed behavior; this Lexicon entry only routes to it. |
| **Clearance** | The actor-level cap on permitted operations, intersected with current Canon, assignee/tool permissions, and explicit owner scope; a Job Order carries that authority but cannot enlarge it. The declared classes are observer, auditor, pawn, steward, engineer, and owner, and machine enforcement may be claimed only for operations controlled by a running policy consumer ([ADR-0005](workbench/docs/adr/0005-machine-enforcement-requires-running-consumers.md), [ADR-0009](workbench/docs/adr/0009-job-order-authority-is-an-intersection.md)). |
| **Workbench Contract** | The portable distribution boundary consisting of seven root files: `AGENTS.md`, `BLUEPRINT.md`, `LEXICON.md`, `RUNBOOK.md`, `TASKBOARD.md`, `CLAUDE.md`, and `README.md`, with the six-lane `workbench/` support directory — `docs/`, `specs/`, `wiki/`, `sessions/`, `feedback/`, and `tools/`; the project index remains routing ([ADR-0016](workbench/docs/adr/0016-project-index-remains-routing.md)). The file set has no Governance Plane of its own, and `LEXICON.md` serves as this workspace's shared context and vocabulary map ([ADR-0013](workbench/docs/adr/0013-seven-file-workbench-contract.md), [ADR-0017](workbench/docs/adr/0017-workbench-support-directory-has-six-lanes.md); item 49). |
| **Governance Stack** | Governance Planes, Authority Order, Clearance, and Job Order read together to assign roles and bound work in one operation. This governance section carries their standalone definitions and links to rationale for roles, binding rules, and the shared policy source ([ADR-0001](workbench/docs/adr/0001-planes-classify-operations-not-artifacts.md), [ADR-0002](workbench/docs/adr/0002-binding-rules-stay-in-current-controls.md), [ADR-0004](workbench/docs/adr/0004-policy-data-and-derived-matrix.md), [ADR-0006](workbench/docs/adr/0006-extend-the-existing-clearance-policy.md); items 36/58). |
| **Governance passage** | The applicable ordered path of work inward through Projection → Intent → Enduring Context → Grounding → Canon → Actuality and outward through Actuality → Grounding → Canon → Enduring Context → Intent → Projection. Inapplicable planes may be explicitly skipped without another artifact, approval, or gate, while preserving provenance and any evidence the destination requires (notepad item 15A). |
| **CRUD** | Create, Read, Update, and Delete, all available across the six planes subject to the operation's conditions and authority. Append-only, supersession, and generation rules are conventions for particular artifacts and do not remove a CRUD operation from an entire plane ([ADR-0003](workbench/docs/adr/0003-full-crud-with-artifact-conditions.md)). |
| **Prose** | Unstructured natural-language text: an encoding independent of an operation's Governance Plane. Machine enforcement requires structured policy and a running consumer that evaluates it and controls the operation ([ADR-0005](workbench/docs/adr/0005-machine-enforcement-requires-running-consumers.md)). |
| **Operation** | A unit of work distinguished by its target and required evidence, with artifacts assigned governance roles for that work. Promote, ground, settle, and project name operations; this category does not settle their individual meanings or CRUD mappings ([ADR-0007](workbench/docs/adr/0007-verbs-name-operations.md)). |
| **`promote`** | The operation that moves an artifact to its place in the Workbench Contract, generally inward toward Actuality, without inherently increasing authority. For a grilling, promotion is explicit and per item: accepted ADRs and SPECs provide Grounding, the originating notepad rests as Enduring Context, and unpromoted items gain no authority ([ADR-0007](workbench/docs/adr/0007-verbs-name-operations.md), [ADR-0008](workbench/docs/adr/0008-adrs-and-specs-record-grounding.md); item 22). |
| **ADR** | An architectural decision record in `docs/adr/` that serves as Grounding for a durable decision and its rationale. Its binding requirements land in the owning controls in the same pass; a superseded ADR stays in place, marked and pointing to its successor ([ADR-0002](workbench/docs/adr/0002-binding-rules-stay-in-current-controls.md), [ADR-0008](workbench/docs/adr/0008-adrs-and-specs-record-grounding.md); items 16/56/57). |
| **SPEC** | A stable capability record serving as Grounding for the intended outcome, requirements, acceptance, and evidence. It supplies no independent authorization, and when edited it is the operation's Actuality target ([ADR-0001](workbench/docs/adr/0001-planes-classify-operations-not-artifacts.md), [ADR-0008](workbench/docs/adr/0008-adrs-and-specs-record-grounding.md)). |
| **Clearance band** | The actor-level grant fixing what counts as Actuality for that actor and their CRUD per artifact kind under the Governance Stack. A Job Order links to this grant so the operation checklist uses its owning source ([ADR-0012](workbench/docs/adr/0012-job-orders-link-to-owning-sources.md); item 54). |

## Runtime, routing, and recovery

| Term | Meaning |
|---|---|
| **Heartbeat** | The Servitor's literally monitored two-way pulse. Foundry emits an atomic L0-L3 load, active-worker, average/peak reasoning, declared-cadence, sequence, emitted-time, source, and freshness snapshot; CIC acknowledges the exact sequence and returns observer health/freshness. Exact cadence is L0=60s, L1=15s, L2=5s, L3=1s. One missed expected beat is immediately down: Lighthouse becomes dark/still and preserves last-received time. This is distinct from L0 asleep. (Item 34; 2026-08-30 promotion.) |
| **Mirror dimensions** | The three independent things a Mirror shows, never inferred from one another: **liveness** (heartbeat present or absent), **activation** (L0–L3 brightness and/or pulse tempo), and **operational state** (queued, working, blocked, failed, verified, stale). (Items 11, 34.) |
| **Announced Activation** | The *No Silent Wake* invariant: every activation transition is announced to the Mirror socket before or as it happens, and an activation CIC observes but was never told about is itself an anomaly alarm. A failsafe in both directions. Announcements are Grounding Journal events, so the failsafe rides the existing ledger rather than a new pipe. (Item 35.) |
| **Lighthouse** | The locked owner-visible Foundry activity surface. Its sweep represents a fresh declared Heartbeat observation; brightness/label preserves meaning for reduced motion, screenshots, and print. One missed expected beat makes it dark/still while exact last-received time remains visible. It must distinguish live, quiet, stale, unavailable, source-mismatched, and unauthenticated states and never substitute PID/HTTP availability, a generic task feed, Schematic animation, or historical Canon for lifecycle Actuality. Foundry S-003 owns the portable contract; private bindings and evidence remain instance-owned. |

| **Scout Status** | The standardized Taskboard report left by a Scout: one disposition (`healthy`, `agent-action`, `owner-attention`, `blocked`, or `unverified`), freshness, evidence links, and next handoff. |
| **Checkpoint** | A truthful commit and push of incomplete but recoverable task work before an agent yields or changes lanes. |

Authoring either never ends a session, promotes Canon, or opens a claim. |
| **Flight handoff** | A uniquely sequenced, append-only stage receipt under one Spec-local Job Order's `handoffs/`.
